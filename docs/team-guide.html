01ทำไมต้องทำโปรเจกต์นี้

คนเป็นภูมิแพ้และหอบหืดใช้เวลาส่วนใหญ่ในห้อง และต้องการรู้ว่า "ตอนนี้อากาศในห้องกำลังจะทำให้ฉันมีอาการหรือเปล่า" ซึ่งเครื่องวัดฝุ่นทั่วไปตอบไม่ได้ เพราะมันบอกแค่ตัวเลข ไม่ได้บอกว่าตัวเลขนั้นผิดปกติสำหรับห้องนี้หรือไม่

ปัญหาที่ผู้ป่วยเจอจริง

  • อาการมาก่อนที่ตัวเลขจะเกินเกณฑ์ — มาตรฐานตั้งไว้สำหรับประชากรทั่วไป คนแพ้ไวมีอาการที่ค่าต่ำกว่านั้น
  • ไม่รู้ว่าอะไรเป็นตัวกระตุ้น — ฝุ่น? ควันธูป? น้ำยาถูพื้น? ความชื้นที่ทำให้ไรฝุ่นเยอะ?
  • ไม่มีหลักฐานไปคุยกับหมอ — บอกได้แค่ "รู้สึกแย่ตอนกลางคืน"

02ทำไม if-else ไม่พอ

คำถามแรกที่กรรมการจะถามคือ "ทำไมไม่เขียน if (pm25 > 37.5) alert();"

สถานการณ์threshold บอกว่าความจริงประเภท
PM2.5 = 60 ตอนเที่ยง ฤดูเผาผิดปกติ! ปกติของฤดูกาลนั้น เตือนไปก็ไม่มีประโยชน์contextual
PM2.5 = 25 ตอนตี 3 ในห้องแอร์ปิดสนิท ปกติ ผิดปกติมาก — มีอะไรเผาไหม้ หรือมีคนเข้าห้องcontextual
TVOC พุ่ง 3 เท่าใน 20 วิ แล้วลงช้าๆ 10 นาทีปกติถ้าไม่เกินเพดาน สเปรย์/แอลกอฮอล์/น้ำยาทำความสะอาด — ตัวกระตุ้นภูมิแพ้ชัดเจนcollective
PM2.5 ค้างที่ 8.0 นิ่งสนิท 6 ชั่วโมงปกติมาก เซนเซอร์พัง — พัดลมตันหรือสาย UART หลุดsensor fault
RH 85% ต่อเนื่อง 3 วัน PM ปกติปกติ สภาวะที่ไรฝุ่นและเชื้อราขยายพันธุ์ — ความเสี่ยงระยะยาวของคนภูมิแพ้contextual
🔑 แนวคิดหลัก เราไม่ได้ถามว่า "ค่านี้สูงไปไหม" แต่ถามว่า "รูปแบบอากาศช่วง 5 นาทีที่ผ่านมา เหมือน 'อากาศปกติของห้องนี้' ที่เราเห็นมา 2 สัปดาห์ไหม"

ให้ autoencoder เรียนบีบอัดข้อมูลปกติแล้วสร้างกลับ — ปกติจะสร้างกลับได้แม่น ผิดปกติจะสร้างกลับไม่ได้ → reconstruction error สูง = ผิดปกติ
ข้อดี: ไม่ต้องรู้ล่วงหน้าว่า anomaly หน้าตายังไง จึงจับสิ่งที่ไม่เคยเห็นได้

03นิยาม "ผิดปกติ" 3 แบบ

A. Environmental Event

จุดธูป/ยากันยุง · ทำอาหาร · สูบบุหรี่ · สเปรย์ · กวาดบ้าน · เปิดหน้าต่างช่วงรถติด

จับด้วย: AE reconstruction error + ความสัมพันธ์ข้ามช่องสัญญาณ
✅ สร้างเองได้ → เป็นแหล่ง label หลัก

B. Sensor / System Fault

พัดลม PMS ตัน · สาย UART หลุด · checksum error · ค่าค้าง · ไฟตก

จับด้วย: rule-based (std=0, frame หาย, ค่านอกช่วง) — ไม่ใช้ AE

C. Slow Drift

MOX sensor เสื่อม · ฝุ่นเกาะเลนส์เลเซอร์

จับด้วย: เทียบสถิติรายวันกับ baseline + rolling normalization
⚠️ ห้ามให้ AE จับข้อนี้

⚠️ กับดักที่ทำให้โปรเจกต์พังสัปดาห์ที่ 10 ถ้าเอา drift (C) ไปให้ autoencoder จับ → ผ่านไป 3 สัปดาห์โมเดลจะเตือนตลอดเวลา เพราะการกระจายของ input เลื่อนไปจาก training set แล้ว (concept drift)
คนจะคิดว่า "โมเดลห่วย" แล้วไปแก้โมเดล ทั้งที่ปัญหาคือเอากลไกผิดประเภทมาใช้
→ ต้องแยกกลไก และ normalize ด้วย rolling statistics ไม่ใช่ค่าคงที่จากวันแรก

4.2 Dataset ที่ต้องเก็บเอง — สินทรัพย์ที่มีค่าที่สุด

Phase A — Baseline "ปกติ"

  • เก็บ ต่อเนื่อง ≥ 14 วัน ที่ 1 Hz
  • ห้ามขยับตำแหน่งเซนเซอร์
  • ⚠️ ทิ้งข้อมูล 24–48 ชม.แรก (burn-in ของ ENS160)
  • เป้า uptime > 95%
  • ใช้เป็น training set

Phase B — Induced Anomaly

  • 9 การทดลอง × 3 รอบ = 27 events
  • จดเวลาเริ่ม–จบตรง NTP
  • เก็บใน events.csv แยกจากข้อมูลดิบ
  • ใช้เป็น evaluation set เท่านั้น
  • 🏆 ปล่อยเป็น open dataset ได้
🏆 ทำไม dataset นี้มีค่ามาก ยังไม่มี labeled indoor air-quality anomaly dataset สาธารณะที่มี ground truth จากเหตุการณ์ที่จงใจสร้าง งานที่มีอยู่ใช้ label แบบคาดเดาหรือใช้เกณฑ์สถิติ → ถ้าปล่อยบน GitHub/Zenodo จะเป็นสิ่งที่คนอื่นเอาไปอ้างอิงได้จริง และทำให้ใบสมัคร ป.โท / สหกิจ ของทั้ง 3 คนโดดเด่นกว่าโปรเจกต์นักศึกษาทั่วไป

09CO และแก๊สอันตรายถึงชีวิต

🔴 เส้นแบ่งที่ห้ามข้าม — อ่านก่อนทำอย่างอื่น เครื่องที่เราสร้างไม่ใช่ CO alarm และห้ามเรียกแบบนั้น

CO alarm ที่ขายจริงต้องผ่าน UL 2034 หรือ EN 50291 ซึ่ง ตัดสินที่อัลกอริทึม ไม่ใช่ว่าเซนเซอร์อ่านค่าได้: เตือนตามเส้นโค้งความเข้มข้น–เวลาที่กำหนด · ไม่เตือนผิดจากไอระเหยอื่นในบ้าน · ทำงานได้ในความชื้นสูงโดยเวลาตอบสนองไม่ช้าลง · มีแบตสำรอง · มีสัญญาณเตือนตอนเซนเซอร์หมดอายุ

🔑 เซนเซอร์เปล่าคือ "ชิ้นส่วน" ไม่ใช่ "อุปกรณ์นิรภัย"

กฎ 4 ข้อของทีม

  1. ถ้าทำการทดลองที่มีการเผาไหม้ (E1 จุดธูป · E2 ทำอาหาร) ต้องมี CO alarm ที่ได้มาตรฐานอยู่ในห้องด้วย — ข้อนี้ควรทำอยู่แล้วแม้ไม่ได้ติดเซนเซอร์
  2. ห้ามเขียนหรือพูดว่าเครื่องนี้ "เตือนภัย CO ได้" ทั้งในรายงาน สไลด์ โปสเตอร์ และ README → ใช้คำว่า "บันทึกและติดตามระดับ CO เพื่อการวิจัย"
  3. ติดป้ายบนตัวเครื่อง: "อุปกรณ์วิจัย — ไม่ใช่เครื่องเตือนภัย ห้ามใช้แทน CO alarm ที่ได้มาตรฐาน"

9.3 🔴 ห้ามทดสอบด้วยการสร้าง CO เอง

ห้ามเด็ดขาด ❌ ห้ามเผาอะไรในห้องปิดเพื่อดูว่าเซนเซอร์ขึ้นไหม · ❌ ห้ามใช้ไอเสียรถ เตาถ่าน หรือเครื่องทำน้ำอุ่นแก๊สเป็นแหล่งทดสอบ · ❌ ห้ามทดสอบในห้องน้ำหรือพื้นที่อับอากาศ

เหตุผล: CO ไม่มีสี ไม่มีกลิ่น ไม่มีรส — คุณจะไม่รู้ตัวจนกระทั่งสายเกินไป และอาการเริ่มต้น (ปวดหัว มึน) ทำให้ความสามารถตัดสินใจแย่ลง ผู้ที่ได้รับ CO จึงมักช่วยตัวเองไม่ได้
วิธีทดสอบที่ปลอดภัยทำอย่างไรได้อะไร
🔑 1. ทดสอบทางไฟฟ้า ป้อนแรงดันจำลองเข้าขา analog หรือส่งเฟรม UART จำลอง ✅ ทดสอบ logic การเตือนได้ครบ 100% โดยไม่ต้องมี CO จริงแม้แต่โมเลกุลเดียว
2. Co-locationวางข้าง CO alarm ที่ได้รับรอง แล้วบันทึกทั้งคู่เทียบเคียงในสภาพจริงอย่างปลอดภัย
3. บันทึกระยะยาวปล่อยเก็บข้อมูล 14 วันได้ baseline และเห็น drift
4. แก๊สสอบเทียบถังแก๊สมาตรฐานความเข้มข้นที่ทราบค่า ⚠️ ต้องอยู่ภายใต้การดูแลของอาจารย์ ในห้องแล็บที่มีตู้ดูดควันเท่านั้น
✅ เขียนในรายงานแบบนี้ "ทดสอบ logic ด้วยข้อมูลจำลอง ส่วนการตอบสนองต่อ CO จริงไม่ได้ทำการทดสอบด้วยเหตุผลด้านความปลอดภัย"
→ นี่คือคำตอบที่ถูกต้องทางวิศวกรรม ไม่ใช่จุดอ่อนของโปรเจกต์

แก้ปัญหา contextual anomaly ตรงจุด: PM2.5 = 60 ตอนฤดูเผาไม่ผิดปกติ แต่ถ้าข้างนอก 20 ในห้อง 60 → ผิดปกติแน่นอน
⚠️ limitation: สถานีนอกอาคารที่ใกล้ที่สุดอาจห่างหลายกิโลเมตร และเป็นข้อมูลรายชั่วโมง → ต้อง interpolate และระบุว่าเป็น proxy

⚠️ ความชื้นยังต้องระวัง (แม้เบากว่า outdoor) งานวิจัยใน Atmospheric Measurement Techniques (2024) พบว่า ที่ RH เกิน ~75% เซนเซอร์ Plantower อ่าน PM สูงเกินจริง (hygroscopic growth)

✅ ใส่ RH + absolute humidity เป็น feature → ทำ ablation เทียบ false-alarm rate มี/ไม่มี feature นี้ → เปลี่ยนจากบั๊กเป็นคำถามวิจัย
