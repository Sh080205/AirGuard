# AirGuard-S3 — แบ่งงาน 3 คน + prompt สำเร็จรูป

**อัปเดต:** 1 ก.ย. 2569 · เหลือ ~13 สัปดาห์ถึงส่งงาน

---

## 🎯 โปรเจกต์นี้ทำไปทำไม

> **เครื่องเฝ้าระวังคุณภาพอากาศในห้องสำหรับผู้ป่วยภูมิแพ้และโรคทางเดินหายใจ
> ที่ตรวจจับ "รูปแบบผิดปกติ" ไม่ใช่แค่ "ค่าเกินเกณฑ์"**

### ปัญหาที่แก้

เครื่องวัดอากาศที่มีขายทั่วไปทำงานแบบ `ถ้า PM2.5 > 50 ให้เตือน`
แต่สำหรับคนเป็นภูมิแพ้ **สิ่งที่กระตุ้นอาการหลายครั้งไม่ได้ทำให้ค่าไหนเกินเกณฑ์เลย**

```
┌──────────────────────────────────────────────────────────┐
│  ทำอาหาร                                                  │
│    PM2.5 ↑↑   อุณหภูมิ ↑   ความชื้น ↑                      │
│    → ขึ้นพร้อมกัน มีเหตุผล = สภาพปกติของห้องครัว            │
├──────────────────────────────────────────────────────────┤
│  ปัดฝุ่น / เชื้อราฟุ้ง / เปิดตู้ที่ไม่ได้เปิดนาน                  │
│    PM2.5 ↑↑   อุณหภูมิ →   ความชื้น →                      │
│    → ฝุ่นขึ้นลอยๆ ไม่มีอะไรมาด้วย = ผิดปกติ 🔴              │
└──────────────────────────────────────────────────────────┘
```

**ทั้งสองกรณี PM2.5 อาจอ่านได้เท่ากันเป๊ะ** — เกณฑ์ตัวเลขแยกไม่ออก
แต่ถ้าดู**ความสัมพันธ์ระหว่างตัวแปร** จะเห็นว่าอันหนึ่งปกติ อีกอันไม่ปกติ

> 🔑 **นี่คือเหตุผลทั้งหมดของโปรเจกต์** — เราเคยจำลองแล้วพบว่า
> **3σ แบบดูทีละตัวจับ anomaly ประเภทนี้ได้ 0% · Mahalanobis จับได้ 100%**
> ถ้าโปรเจกต์จบลงที่ `if (pm25 > 50)` แปลว่าทำผิดทาง

### เป้าหมาย 3 ชั้น

| ชั้น | เป้าหมาย | วัดผลยังไงว่าสำเร็จ |
|---|---|---|
| 🏥 **เพื่อผู้ใช้** | เตือนก่อนอาการกำเริบ ไม่ใช่หลังจากนั้น | MTTD ต่ำ · false alarm/วัน ต่ำพอที่คนจะไม่ปิดเครื่องทิ้ง |
| 🎓 **เพื่อเกรด** | บรรยาย: คำนวณ timing/ADC/baud ได้<br>แล็บ: **วัดได้จริงและอธิบายความคลาดเคลื่อนเป็น** | สองวิชาแยกเกรดกัน · ตัวเลขที่วัดเองคือส่วนที่ทำคะแนน |
| 💼 **เพื่อ portfolio** | ESP32-S3 + TinyML บนบอร์ดที่ออกแบบเอง | มีของโชว์ได้ · ต่อยอดกับงาน TCN/PM2.5 บน FPGA ได้ |

### เส้นที่ขีดไว้ชัด — ไม่ใช่อะไร

🔴 **ไม่ใช่เครื่องเตือนภัย CO** — CO ใส่มาเพื่อจับมลพิษที่อันตรายถึงชีวิต
แต่**ต้องแยก safety path ออกจาก ML path** และห้ามอ้างว่าใช้แทน
CO alarm มาตรฐาน UL 2034 / EN 50291 *(Winsen เองก็ห้ามในคู่มือ)*

🔴 **ไม่ใช่เครื่องมือแพทย์** — เป็นเครื่องเฝ้าระวังสภาพแวดล้อมเพื่อการวิจัย

### ทำไมต้อง "ในห้อง" ไม่ใช่ "นอกอาคาร"

เคยคิดจะวัดนอกอาคาร แต่**ทำแล้วพังทั้งวิธีการ** — เพราะจะเทรนและวัดผลได้
ต้องรู้ว่าช่วงไหนคือ anomaly จริง **ในห้องเราสร้าง anomaly ได้เอง**
(จุดธูป ทอดของ ปัดฝุ่น ปิดห้อง) แล้วกดปุ่ม MARK บันทึกเวลาไว้
→ ได้ ground truth · นอกอาคารทำแบบนี้ไม่ได้ ได้แต่เดา

> 📌 นี่คือเหตุผลที่บอร์ดมี **ปุ่ม MARK** — มันคือเครื่องมือสร้าง label ไม่ใช่ปุ่มประดับ

## 🎯 หลักการแบ่งงาน

> **แบ่งตาม "ใครถูกบล็อกด้วยอะไร" ไม่ใช่ตามความถนัด**

บอร์ดยังไม่มา = ใครก็ตามที่งานต้องรอบอร์ด จะว่างไป 2–3 สัปดาห์
เพราะงั้นต้องจัดให้ **ทั้งสามคนมีงานที่เริ่มได้วันนี้**

```
                    ┌─────────────────────────────────────┐
สัปดาห์ 1–3         │  ทั้ง 3 คนทำขนานกัน ไม่มีใครรอใคร     │
(บอร์ดยังไม่มา)      │  A: ฮาร์ดแวร์+จัดซื้อ                 │
                    │  B: firmware ที่ยังไม่ต้องมีบอร์ด      │
                    │  C: ข้อมูล+โมเดล (ไม่ต้องมีบอร์ดเลย)   │
                    └─────────────────────────────────────┘
                                    ↓
สัปดาห์ 4           🔗 จุดบรรจบที่ 1 — บอร์ดมา A บัดกรี B เอาโค้ดลง
                                    ↓
สัปดาห์ 5–9         A+B เก็บข้อมูลจริง  →  ส่งให้ C เทรน
                                    ↓
สัปดาห์ 10          🔗 จุดบรรจบที่ 2 — C ส่งโมเดลให้ B ยัดลงบอร์ด
                                    ↓
สัปดาห์ 11–13       ทั้ง 3 คน: ทดสอบ · วัดผล · เขียนรายงาน
```

```
เราจะเขียนเฟิร์มแวร์ ESP-IDF สำหรับบอร์ด AirGuard-S3
เครื่องวัดคุณภาพอากาศในห้อง + anomaly detection บน ESP32-S3-DevKitC-1 (N16R8)

【 สภาพแวดล้อม 】
- ESP-IDF v5.5.x (ไม่ใช่ v6)
- ยังไม่มีบอร์ดจริง → โค้ดต้อง build ผ่านและ test ผ่านโดยไม่ต้องมีฮาร์ดแวร์

【 สิ่งที่ต้องสร้าง เรียงตามลำดับ 】
1. โครง ESP-IDF project + CI (GitHub Actions) ที่ build ผ่าน
2. components/pms7003/ — driver PMS7003
   - parse frame 32 ไบต์ ตรวจ checksum
   - 🔑 แยกส่วน parse ออกจากส่วน UART ให้ unit test ได้โดยไม่ต้องมีบอร์ด
3. test/ — unit test ของ parser ด้วย frame ปลอม
   ต้องมีเคส: frame ถูกต้อง / checksum ผิด / frame ขาด / มีขยะนำหน้า
4. main/ — FSM: BOOT → WARMUP → NORMAL → WATCH → ALARM
   + FreeRTOS task แยก: sensor / logic / io
5. components/storage/ — เขียน CSV ลง microSD

【 กฎการเขียนโค้ด 】
- 🔴 เช็ค esp_err_t ทุกจุด ใช้ ESP_ERROR_CHECK() หรือจัดการ error เอง
  โค้ดที่ไม่เช็ค return คือโค้ดผิด
- 🔴 ใน ISR: ห้าม printf/ESP_LOG · ห้าม delay · ห้าม malloc · ห้าม float
  ISR ต้องสั้น ส่งงานต่อให้ task ผ่าน queue · พิจารณา IRAM_ATTR
- 🔴 ตัวแปรที่ ISR กับ task ใช้ร่วมกัน: volatile อย่างเดียวไม่พอ

## 🅲 คน C — ใช้ Claude Code *(ML)*

```
เราจะทำ pipeline anomaly detection สำหรับข้อมูลคุณภาพอากาศในห้อง
รันบน ESP32-S3 ตอนสุดท้าย (TinyML, int8) แต่ตอนนี้ทำบน PC ก่อน

【 ข้อมูล 】
- ยังไม่มีข้อมูลจริง บอร์ดยังไม่เสร็จ
- feature: pm1_0, pm2_5, pm10, temp_c, humidity_pct,
           tvoc_ppb, eco2_ppm, co_ppm
- unsupervised — เทรนด้วยข้อมูลปกติอย่างเดียว

【 สิ่งที่ต้องสร้าง เรียงตามลำดับ 】
1. ml/synth.py — สร้างข้อมูลปลอมที่สมจริง พร้อมฝัง anomaly 3 แบบ:
   ก. ค่าพุ่งทีเดียว (จุดธูป/ทำอาหาร)
   ข. ค่าค่อยๆ ไต่ขึ้น (ห้องปิด CO2 สะสม)
   ค. ความสัมพันธ์ระหว่างตัวแปรเพี้ยน แต่แต่ละตัวยังอยู่ในช่วงปกติ
   🔑 แบบ ค. คือเหตุผลทั้งหมดที่ต้องใช้ multivariate — 3σ ตัวเดียวจับไม่ได้

2. ml/metrics.py
   🔴 ห้ามใช้ accuracy — ข้อมูลไม่สมดุลรุนแรง ทายว่าปกติตลอดก็ได้ 99%
   🔴 ห้ามใช้ Point Adjustment — Kim et al. AAAI 2022 แสดงว่ามันทำให้
      โมเดลสุ่มดูเหมือนชนะ SOTA ถ้าใช้จะโดนจับได้
   ต้องมี: PR-AUC · event-level detection rate · MTTD (เวลาเฉลี่ยกว่าจะจับได้)
           · false alarm ต่อวัน · precision/recall ที่ threshold ที่เลือก

3. ml/baseline.py — 3σ ตัวเดียว และ Mahalanobis distance
   🔑 ต้องมี เพื่อพิสูจน์ว่า autoencoder ดีกว่าจริง ไม่ใช่แค่ซับซ้อนกว่า

4. ml/train_ae.py — autoencoder + threshold จาก reconstruction error
   + persistence rule (ต้องผิดปกติติดกันกี่ครั้งถึงจะเตือน)

5. เทียบผลทั้ง 3 วิธีบนข้อมูลปลอมชุดเดียวกัน ออกเป็นตาราง + กราฟ

【 กฎ 】
- Python + NumPy/pandas/scikit-learn/PyTorch + matplotlib
- ทุกไฟล์ต้องรันได้จริง ไม่ใช่โค้ดที่ดูดีแต่รันไม่ผ่าน — รันให้ดูด้วย
- 🔴 ตั้ง random seed ทุกที่ ผลต้องทำซ้ำได้
- 🔴 แยก train/validation/test ตามเวลา ห้ามสุ่มแบ่ง
  ข้อมูล time-series ถ้าสุ่มแบ่งจะเกิด data leakage ผลจะดูดีเกินจริง
- อธิบาย intuition ของทุกสูตรที่ใช้ ไม่ใช่แค่เขียนโค้ด
  เพราะต้องเอาไปเขียนรายงาน
- ทำทีละขั้น เสร็จแล้วหยุดรอผมรีวิว

เริ่มจากขั้นที่ 1 และ 2 พร้อมกัน เพราะต้องใช้ข้อมูลปลอมมาทดสอบ metrics
